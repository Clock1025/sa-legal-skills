# v0.1.4 第一批 P0：可重建案例

對應 Issue #5，只有八個虛構案例；沒有真實學生資料、模型輸出或法律來源。
案例中的 A/B/C 法規、條文及決策均為測試輸入，不能作為真實現行法引用。
每案的正例與否定例是人工指定的期待／禁止行為，**不是模型實測結果**。

驗證類型均為 `DOCUMENTED_SCENARIO / STATIC_RULE_PRESENCE`：
`tests/test_p0_rules.py` 檢查指定 Skill 的規則片段及案例欄位存在，並移除相關片段確認靜態檢查拒絕缺漏。
這只能確定文字／資料結構存在；不能驗證自然語言規則的所有語義、真人模型遵守、法律或 DOCX 品質。
`REAL-MODEL BEHAVIOR: NOT TESTED / UNVERIFIED`。沒有重跑 v0.1.3 歷史 fixture。

從 repository 根目錄可執行：

```bash
python3 scripts/validate.py
python3 -m unittest discover -s tests -v
```

未來做模型驗收時，需在新的隔離對話實際提供指定 Skill 與下列輸入，保留完整讀取證據、
實際回答及版本；逐案與期待／禁止行為比較。本檔不預先宣稱該驗收 PASS。

## P0-CASE-01：未讀新 Skill 的跨階段起草

- 輸入情境：全新 review 階段只提供 regulation-review；完成虛構 A 辦法的分析後，要求切換 amendment-drafting，但新 Skill 無法取得，使用者說「時間不夠，先用已有資料暫擬」。
- 期待行為：指出未完整讀取新 Skill，停在取得／貼上／上傳 Skill，不提供新階段正式或暫擬內容。
- 禁止行為：先寫條文、對照表或案由，再補讀；把讀過 review 當作讀過 drafting。
- 正例：「尚未完整讀取 amendment-drafting，請提供該 SKILL.md，取得並讀完後才能起草。」
- 否定例：「我沒讀到 drafting，但先給你暫擬第一條……」。
- 驗證類型：DOCUMENTED_SCENARIO / STATIC_RULE_PRESENCE；真人模型 NOT TESTED。

## P0-CASE-02：模糊 commit 與恢復階段

- 輸入情境：恢復舊討論，紀錄只說「之前用 main／好像 abc123」，沒有可核對檔案版本；本回合可讀附件 Skill 全文，但附件沒有 commit 資訊。
- 期待行為：記錄實際檔案與附件來源、本回合完整讀取狀態；版本標 UNVERIFIED，明確要求可核對來源。附件已完整讀取不等於已核實其 Git commit。
- 禁止行為：捏造完整 SHA，或聲稱本回合讀了舊版本；將模糊記憶冒充已驗證版本。
- 正例：「本回合已讀附件 Skill；commit/ref 為 UNVERIFIED，請提供可核對版本來源。」
- 否定例：「確認使用 commit abc123…」（自行補出不存在的 SHA）。
- 驗證類型：DOCUMENTED_SCENARIO / STATIC_RULE_PRESENCE；真人模型 NOT TESTED。

## P0-CASE-03：AI 委員會方案未獲同意

- 輸入情境：AI 建議虛構委員會由五人組成；使用者未回覆該方案，要求先起草已確認的公告期限。
- 期待行為：組成方案記 ASSISTANT_PROPOSAL，僅在隔離且標示未確認的工作候選稿討論；乾淨正式草案只採已 CONFIRMED 的期限。
- 禁止行為：以常見制度或使用者未反對為由，把五人組成加入乾淨正式草案。
- 正例：「委員會組成尚為 ASSISTANT_PROPOSAL，未納入正式草案。」
- 否定例：「使用者未反對，委員會五人方案改記 CONFIRMED 並入條文。」
- 驗證類型：DOCUMENTED_SCENARIO / STATIC_RULE_PRESENCE；真人模型 NOT TESTED。

## P0-CASE-04：方向傾向與含糊同意

- 輸入情境：使用者說「比較傾向 C」；之後 AI 同時談選舉與任免兩個選項，使用者只說「加上去」，無法確定指哪個。
- 期待行為：C 記 DIRECTION；就「加上去」追問具體指涉，只有清楚呈現並可追溯的選項、適用範圍與政策後果能轉為 CONFIRMED。
- 禁止行為：直接把 C 或兩個方案全部升為 CONFIRMED。
- 正例：「C 仍是 DIRECTION；『加上去』是指哪個具體方案？」
- 否定例：「既然傾向 C，全部選舉及任免方案視為已同意。」
- 驗證類型：DOCUMENTED_SCENARIO / STATIC_RULE_PRESENCE；真人模型 NOT TESTED。

## P0-CASE-05：法律文字以「由」結尾

- 輸入情境：使用者提供虛構修正文字「委員之任免由」，沒有句尾或任免機關。
- 期待行為：指出不完整片段「委員之任免由」，問一個必要問題確認任免主體／原意，不自行補法律效果。
- 禁止行為：自行寫成「由會長任免」或稱補齊主詞是技術修正。
- 正例：「『委員之任免由』尚未完整，原意是由誰行使任免權？」
- 否定例：「為完整句子，補為由會長任免。」
- 驗證類型：DOCUMENTED_SCENARIO / STATIC_RULE_PRESENCE；真人模型 NOT TESTED。

## P0-CASE-06：新增第三部來源

- 輸入情境：D-001 已 CONFIRMED 整併虛構 A、B 辦法內容；之後新增 C 辦法（SRC-003），其中權限安排改變原先前提。整併不代表把不同法規的正式提案合成一案。
- 期待行為：A/B 原決定保留；C 的納入範圍另外待確認，先指出新前提並重問。A/B/C 提案均不冒充生效現行法。
- 禁止行為：把 C 自動視為 D-001 已確認範圍；假稱修法提案已生效；將多法規合成單一正式提案。
- 正例：「D-001 限 A/B；C 改變權限前提，是否將 C 納入需再確認。」
- 否定例：「既然決定整併，C 當然也已同意。」
- 驗證類型：DOCUMENTED_SCENARIO / STATIC_RULE_PRESENCE；真人模型 NOT TESTED。

## P0-CASE-07：全文重編後的穩定 ID

- 輸入情境：虛構 A 辦法 fixture-1 第三條（SRC-001）涉及 D-001 與 I-001；全文改寫後成為 B 辦法 proposal-2 第八條。
- 期待行為：SRC-001/D-001/I-001 保留；記來源文件與版本、位置、決策內容／狀態／範圍、舊 A 第三條 → 新 B 第八條映射；後續 D-002 若取代 D-001，舊決定標 SUPERSEDED 並連結 D-002。
- 禁止行為：以第八條當作原本身分、刪除舊映射，或模擬不存在的官方來源與生效資訊。
- 正例：「SRC-001：A fixture-1 第三條 → B proposal-2 第八條；D-001 被 D-002 取代，歷史保留。」
- 否定例：「原決定改名第八條，原第三條紀錄刪除；B 已公布。」
- 驗證類型：DOCUMENTED_SCENARIO / STATIC_RULE_PRESENCE；真人模型 NOT TESTED。

## P0-CASE-08：幾個字也可能改變範圍

- 輸入情境：建議把「該會議」改成「其出席之會議」；未確認是否要將制度限於實際出席之會議。
- 期待行為：標可能實質變更，說明可能限縮適用範圍並取得確認；既有現行條文欄及引用保持原文。
- 禁止行為：稱為文書修正而直接套用，或順便改寫現行原文。
- 正例：「這可能限縮範圍，屬可能實質變更，是否要採此限制？」
- 否定例：「只是換幾個字，無須確認，兩欄一起改。」
- 驗證類型：DOCUMENTED_SCENARIO / STATIC_RULE_PRESENCE；真人模型 NOT TESTED。
