# v0.1.2 回歸測試紀錄

本紀錄涵蓋 v0.1.2 的新手 cold-start、DOCX 結構與正式中文字型渲染驗收，以及初測後的修正與重測。

下列實測及人工驗收結果依使用者提供的已完成紀錄整理；不是本輪自動化測試。本輪閱讀目前工作目錄的差異、[START-HERE](../../START-HERE.md)、[新手指南](../first-time-user.md)與 [amendment-drafting](../../skills/amendment-drafting/SKILL.md)，但未重新執行模型對話、產生 DOCX 或進行 Word／PDF 驗收。未記錄的測試日期、模型版本、工具版本及測試 commit 不另行推測。各次結果只代表當次環境，不保證平台或模型的永久能力。

## 結果分類與統計原則

- **PASS**：當次測試達到所列要求。
- **FAIL**：有效測試暴露未達要求的行為。重測中的 **FAIL / PARTIAL** 保留部分改善與仍未通過的事實，不視為 PASS。
- **INVALID / NOT TESTABLE**：測試入口、上下文或環境不符合要驗證的條件，另列原因，不計入有效 PASS／FAIL 統計。
- **NOT TESTED**：尚未執行或沒有可用的驗收結果，不推定通過。

初測與重測分開統計；不同測試階段或同一組中的多次觀察，不合併成平台整體成功率。DOCX 結構與視覺驗收也分開記錄，不混入 cold-start 統計。

### 表格縮排複查與本版驗收決定

後續人工重新檢查實際 Word／PDF render 時發現，先前的表格縮排人工驗收沒有使用清楚的縮排基準線。放大複查三欄表格「修正條文」欄後，早期 fixture 的以下兩個第二項長文案例首行／續行視覺關係不一致：

- 「第二項 長文字測試……」
- 「第二項補充長文……」

當時因此撤回先前「表格內縮排 PASS」的視覺判定，並列為待複查。後續人工檢視確認表格核心水平縮排可作為本版依據；部分長文字右側邊界仍不完全整齊，依本版發布決定列為非阻斷限制，不要求再產生或渲染 DOCX。DOCX generation、OOXML indentation、一般正文視覺縮排、原文保真、native table、正式中文字型實際渲染及 underline／bold 等已驗項目維持原紀錄。

### 最新人工複查與段落間距（當時待修，後由本版接受）

使用者回報新版表格 fixture 已改善可判讀性：第二項 A／B 的 OOXML paragraph properties 一致，人工視覺複查中兩者的水平縮排行為當時看起來一致。該觀察當時僅屬中間結果，沒有標記為完整表格視覺 regression PASS；本版後續依最終發布決定接受核心排版驗收結果及下述非阻斷限制。

新版 fixture 的表格框線由使用者人工加入，只作 QA 視覺輔助；這不是 fixture 自動產生能力，也不是 Skill 規則。最新人工驗收發現三項格式問題：

1. 行距為 1.5 倍，視覺過寬；無正式範本時 fallback 應為 single／1.0。
2. fixture 使用「第 184 條」、「第 1052 條」等阿拉伯數字或含空格條號，不符合正式文件格式。
3. 現行條文欄將條號與第一項拆成不同 paragraph，不符合目標版面。

因此補充段前／段後均為 0 pt、single／1.0 行距、正式範本優先的 fallback，並明定條號中文數字及條號與第一項合併為同一 paragraph。其後已人工驗收本版核心項目，並接受右側視覺邊界限制；v0.1.2 不再進行額外 DOCX 重測。

後續人工驗收另發現，既有 fixture 的表格格線實際呈現為灰色，並非預期黑色。因此 Skill 的無範本 fallback 已補為黑色（`#000000`），並要求 OOXML 明確指定 `w:color="000000"`，不依賴 theme color 或應用程式預設值。本輪依發布收尾決定，沒有重新產生或重新渲染 DOCX 驗證這項單一色彩修正；其狀態為 **規則已修正，尚未重新驗證**，不是 rendering PASS，也不代表整體 DOCX regression FAIL。

### 已知非阻斷版面限制

實際 Word／PDF 人工驗收中，部分長文字段落的右側視覺邊界不完全整齊。此現象不影響條號、項／款結構、縮排、文字保真、可編輯性或法律內容。可能相關因素包括 Microsoft Word 排版、中文字型、標點避頭尾或行寬計算等渲染行為，但本版尚未確認根因，不將原因全數歸於 Word。v0.1.2 將此列為 **non-blocking known limitation**；後續版本可再研究改善，本版不繼續擴大排版調整。

### 下一輪 fixture 要求

重新測試時依下列條件製作更容易人工判讀的 fixture：

- 所有 fixture、DOCX、PDF、rendered pages 與 inspection output 放在 `test-output/`，不放 repository 根目錄。
- 所有正式測試 paragraph 均設定 `before = 0 pt`、`after = 0 pt`，正文及表格都適用。
- 行距明確設定為 single／1.0；不得預設 1.5 倍行距。
- 條號使用無空格的中文數字格式，不用字元間距模擬排版。
- 修正條文欄、現行條文欄及一般正式條文正文都將條號與第一項置於同一 paragraph，兩者間使用一個 U+3000；第二項及其後仍分別使用獨立 paragraph。
- 同一頁清楚標示每個案例的預期縮排：第一項首行 `0`／續行 `C`；第二項 A 首行 `2C`／續行 `C`；第二項 B 首行 `2C`／續行 `C`。
- 正文與三欄表格分開測試；表格內至少放兩個獨立的第二項長文案例。
- 保留款／目案例；所有正式測試文件均使用獨立 paragraph 維持層級。
- 標楷體與全字庫正楷體都重新產生並實際渲染。
- 可另產 QA-only 版本，以垂直基準線或其他視覺輔助標出 `0`、`C`、`2C`；若框線由人工加入，明確標示為人工 QA 輔助。輔助標示不得影響正式驗收版本。
- 正式驗收版本不得用新增空白或 Tab 模擬縮排。
- 依實際結果驗收，不修改 Skill 規則來迎合測試結果。

測試過程中的暫存產物可辨識為：

- 初版 DOCX fixture。
- 標楷體測試 fixture。
- 全字庫正楷體測試 fixture。

此處只記錄 fixture 類型，不表示其檔案存在或本輪重新驗收。

## 依初測修正

### Skill selection ambiguity

「整套規章」、「未來可能修法」或「想法尚未整理」不應使目前只是檢查現行制度的案件提前進入 `large-scale-reform`。新手入口改以「現在要做的事」選 Skill：

- 目前檢查現行規定、制度或合規問題 → `regulation-review`。
- 已進入整體改革規劃、跨制度協調或大量政策選項追蹤 → `large-scale-reform`。
- 方向大致確定，要起草正式修法文件 → `amendment-drafting`。

### Pre-Skill gate 不夠明確

在本次所需 Skill 尚未取得並完整讀取前，只能辨識大致需求、選 Skill，或協助取得／貼上／上傳 Skill。不得索取法規文本、版本或日期、案件事實、爭議資料及其他正式工作材料，也不得開始正式分析、合規判斷、制度設計或修法起草。

此階段唯一必要下一步是「取得並完整讀取本次所需 Skill」；讀取後才依 Skill 要求逐步取得案件材料。新手指南與 START-HERE 均同步補強門檻。

### Canonical prompt 與 URL UX

START-HERE 曾同時有完整新 prompt 與舊短 prompt，造成可複製入口與測試入口不明確；後續刪除舊版，收斂成唯一標示為「可複製提示詞」的 canonical prompt。

另將 `Skill 來源：https://github.com/Clock1025/sa-legal-skills。` 改為獨立一行的 `Skill 來源：https://github.com/Clock1025/sa-legal-skills`，移除 URL 尾端中文句號，避免介面將句號併入連結。本輪閱讀工作目錄時已確認此形式。
