# Google Docs 優先、DOCX 並存

本指南涵蓋 v0.2.0-alpha.1 基礎及 v0.2.0-alpha.2 母版流程的 prompt-only 文件操作契約，不是 Google Docs 編輯後端。核心最低規範直接放在三份 SKILL.md，ZIP 不需包含本指南即可使用。先完成適用 Skill 的完整讀取，再依案件流程工作；切換文件模式不會切換或放寬法律決策規則。

## 辨識與選擇

先查看實際工具說明與回應，分別記錄建立、讀取、編輯、文件特定權限、版本條件寫入的支援程度。能開網址、搜尋 Drive 或上傳 DOCX 不代表能編輯 Google Docs；模型名稱也不能證明支援。權限未知就標示 UNVERIFIED，不用修改真實文件來試權限。

| 現況 | 下一步 |
| --- | --- |
| 提供既有 Google Docs，支援讀寫與原子版本條件 | 確認文件身分、讀取現況，局部修改原文件 |
| 沒有既有目的文件，且支援安全建立與後續操作 | 按文件請求建立新文件，記錄 ID 並讀回 |
| 提供文件但讀不到、無編輯權限，或缺少安全版本控制 | 停止相關操作、保留現況並回報原因與已完成部分；不擅自建立替代 Google Docs、DOCX 或覆蓋其他文件 |
| 只有讀取能力 | 可以讀取可取得的內容作為材料；不宣稱已寫入 |
| Google Docs 建立、讀取或寫入失敗，或版本衝突無法安全解決 | 停止相關操作，保留現況，回報失敗原因、已完成／未完成部分與不確定結果；不自動轉成 DOCX |
| 使用者明確選擇 DOCX，但無法產生檔案 | 依既有 DOCX 流程提供結構化文字並明列限制，不提供不存在的文件連結 |
| 使用者明確要求 DOCX | 保留原有完整 DOCX 流程 |

分享連結或編輯權限不等於使用者授權修改整份文件。先辨識本次目的文件與範圍；不要把現行法規來源文件直接當作可改寫的草案。讀取相關 tab、section、表格及必要上下文，避免在錯誤位置寫入；讀取不完整時不假裝已核對全篇。

## 每項修改的循環

1. 保留來源版本、政策狀態與範圍，呈現具體修改；只有範圍內已確認內容可進乾淨正式稿。先前明確確認已涵蓋的項目不重問。工作筆記／未決方案與正式稿分開。
2. 每個已確認條文或段落及時處理，不等整份文件；記錄文件 ID、tab／section、條項款目或段落定位、確認依據、修改前後內容與基準 revision。
3. 寫入前重新讀取目標及周邊，檢查人工修改，依新讀取結果與工具索引規則計算精確範圍。重複文字不得直接全域取代；不得預設刪除重建全文。
4. 寫入以新 revision 作原子條件。Google Docs API 的 `writeControl.requiredRevisionId` 不符會拒絕；`targetRevisionId` 允許合併，不能單獨視為拒絕過期修改的同等機制。使用平台工具時須查明它實際提供的等效保護；不捏造參數。單純「讀完立刻寫」仍有競態風險，缺少保護就停止自動寫入、保留現況並回報缺失，不擅自建立任何替代文件。
5. 寫後重新讀取，核對目標文字、段落／表格結構及受影響周邊；區分「請求成功」與「內容已核對」。核對通過後才回報該單元完成。
6. 發生版本衝突時不強制覆寫、不重送舊 request；重讀、比較人工變更與待寫內容。無關的既有確認保留，重疊或政策含義有變才詢問使用者。重新準備安全局部修改前不得繼續寫入。
7. 超時或結果不明時先讀取確認，不盲目重試插入或建立文件。讀回失敗／不符時明列最後已驗證版本、已嘗試變更與未知狀態，停止可能破壞文件的操作；不得整份還原舊快照蓋過新修改。

一項虛構例子：已確認把草案第三條「七日」改為「五日」，基準 revision R1。重讀發現協作者也改了該句期限，就保留現況並釐清重疊修改；若讀取後才有人改動，版本條件應拒絕 R1 寫入。這是預期操作情境，**不是已執行的 API 測試**。

## 雙文件與證據

只有使用者明確選擇 DOCX 才啟動其完整、獨立流程，包括與 Google Docs 同時交付的情況；Google Docs 失敗不構成切換授權。操作失敗時不擅自建立替代 Google Docs、DOCX 或覆蓋其他文件。

法律來源、政策確認、條文層級、原文保真與三欄順序兩模式共用；文件操作不等於正式提案或公布。Google Docs 只調整操作／格式實作，DOCX 原有原生表格、底線、字型、縮排、A4 直式及 QA 規則完整保留。

DOCX 與 Google Docs 同時交付時，註明匯出／生成所依據的已讀回 Google Docs revision、讀取時間及範圍，並核對 DOCX 文字。若 revision 無法取得，標示 UNVERIFIED，說明無法保證並行一致性。這是快照，不是自動雙向同步；不得拿舊 DOCX 覆蓋較新的 Google Docs。格式不支援時揭露限制，不改原文湊排版，也不把 Google Docs 排版宣稱為 Word 視覺驗證。

最小回報：工具／權限、文件身分與版本、已確認修改與實際寫入／讀回項目、未處理部分、衝突或限制、DOCX 快照來源。分開記錄建立、讀取、編輯、衝突處理、讀回保真、DOCX 生成、渲染／字型／視覺 QA。沒有實際操作就標示 `GOOGLE DOCS LIVE OPERATIONS: NOT TESTED`；靜態檢查不能提升此狀態。

官方 API 語義參考：[batchUpdate / WriteControl](https://developers.google.com/workspace/docs/api/reference/rest/v1/documents/batchUpdate#WriteControl)。平台是否暴露這些能力必須以當前工具為準。

## 母版複製與填表（v0.2.0-alpha.2）

[Issue #32](https://github.com/Clock1025/sa-legal-skills/issues/32) 的實作是 Skill 操作規範，讓具備原生工具的平台依序操作；本 repo 不新增後端、OAuth、API Key 管理或第四個 Skill。產生正式提案前仍須完整讀取 `amendment-drafting`，審查／改革 Skill 不因取得母版而取得正式起草權限。

### 1. 輸入、身分與複製

先區分「母版」「現有工作文件」「現行法規來源」。已有目的工作文件時繼續局部修改；使用者明確要求從指定母版製作新提案時，才啟動複製。母版 URL 或連接器授權資源只在當次案件取得，不放進公開 repo、fixtures 或 ZIP。讀取與複製權限分別確認，另核對副本可讀、可局部編輯及可作拒絕過期寫入的原子條件更新。

沒有母版時詢問使用者提供母版／授權資源；沒有原生複製能力、權限不足或無法安全編輯時停止相關操作並回報，不能臆造母版、改建空白替代文件或自動轉 DOCX。若使用者另選非母版流程，依其明確授權處理，不能把它當作本次母版流程成功。

複製只針對使用者指定且授權的母版；原母版唯讀不動。不自動公開分享或更改 ACL。記錄複製回應中的副本 ID，讀回核對副本與母版 ID 不同，再取得副本實際 tab ID、目前 revision、原生內容和編輯權限；不可直接沿用母版 tab ID／index。複製超時或回應不明時，先從已回傳資源或授權目的資料夾查明是否已建立；無法辨識就停下，不盲目重複複製。後續回合沿用已驗證副本。

### 2. 凍結的母版格式契約

以下是 Issue #32 記錄的使用者母版視覺驗收規格；不代表 Codex 看過私人母版，也不代表新產物已驗收。僅用於這組 Google Docs 母版流程，不修改 DOCX 的既有字級／字型規則。

| 區域 | 應設定並讀回核對 |
| --- | --- |
| 紙張 | A4 直式；約 595.28 × 841.89 pt，保留原已驗收頁邊距 |
| 全文字型 | 指定 `DFKai-SB`（標楷體），包含新增表格列及段落 |
| 第一頁標題 | 學生議會關係文書，24 pt |
| 提案正文：案由／說明及其各款／提案人 | 全部 14 pt；依來源及已確認政策填入，未知資料不編造；長文可自然跨頁，不縮字塞入第一頁 |
| 對照表標題 | 〔法規名稱〕修正草案對照表，20 pt，提案內容結束後原生換頁另起新頁，不強制第二頁 |
| 對照表 | 原生可編輯三欄，依序「修正條文｜現行條文｜說明」 |
| 表頭與內文 | 12 pt；三欄等寬且各固定 139.5 pt |

API 回應中的字型名稱只證明設定／讀回值，不能證明渲染實際採用標楷體。Android、iPad、其他平台可能替代字型，未在該裝置查看就標 NOT TESTED。API 不能暴露的版面屬性應列 UNVERIFIED／NOT TESTED，不假造檢查結果；格式缺失不允許改寫原文或自行縮字、改橫式來湊頁面。

### 3. 保留格式、擴列與逐條填入

- 先讀完整相關 tab／section，辨識實際欄位、佔位與樣本文字、表頭、邏輯列、樣式及原生換頁。母版不保證有固定佔位符名稱；不要對整份文件全域取代常見字句。空白不必然是佔位。
- 建立案件內映射：來源版本／條次、確認依據、原文／新文／理由、目的 tab／表格／列／欄、修改前後文字與預期底線。個案資料與私人 ID 不寫回此共用 repo。一法規一正式提案等既有規則照用。
- 已確認一條就及時填入其一個三欄邏輯列，不等全部條文。超過母版初始兩條時用原生操作擴列，插入後重新讀取定位並核對樣式；不假設格式自動繼承。填入三條時應有表頭加至少三個正確對應的資料列，不把第三條塞到前一條的說明欄。
- 每次文字、結構與格式更新都遵守「重讀 → 新 revision 條件寫入 → 讀回」。擴列或刪改文字後重新計算 index；直接 API 的文字 index 使用 UTF-16 code units，不能把 Python 字元數直接當 Google Docs index，也不能忽略原生表格結構索引。只用工具實際支援的參數。
- 保留條／項／款／目獨立段落、原文標點及來源映射。用原生 paragraph／table／text style 排版，不用 Markdown、圖片或空白／Tab 模擬。說明欄就是該條的修正理由，不自動再複製一套逐條理由。
- 替換完成範圍內已辨識的佔位及舊案樣本；未知提案人或法規資料須詢問，該單元保持未完成，不把樣本當事實，也不為清空佔位刪掉人工新增內容。部分寫入可以保留，但交付不得聲稱整份乾淨正式稿完成。

### 原生法規段落縮排與選擇性跨頁控制

依 [PR #33 已確認規格](https://github.com/Clock1025/sa-legal-skills/pull/33#issuecomment-6198736837)，對照表 12 pt 正文以一字暫按 12 pt 計，從儲存格內容左界計算首行／續行：

| 法規層級 | 首行／續行（字） | indentFirstLine／indentStart（pt） |
| --- | --- | --- |
| 第一項（含條號） | 0／1 | 0／12 |
| 第二項及後續無編號項 | 2／1 | 24／12 |
| 款 | 1／2 | 12／24 |
| 目 | 2／3 | 24／36 |

新舊欄都依原文層級套用原生段落樣式。自動換行不是新項；款、目另起段也不是新項，不得把所有換段都當成第二項。不得插入空白／Tab 模擬縮排，也不能把正文已有的結構性 U+3000 當成縮排字元刪掉。擴列、插入文字後重新定位與條件寫入、讀回，再驗實際畫面；數值是本 12 pt 母版的已測設定，不是所有字型的精確字寬。母版仍為佔位時，不先把所有空白段落硬套款目樣式。

只對可容納一頁且不造成大面積留白的短項／款／目，選擇性使用 `keepLinesTogether=true`；長文仍自然跨頁，不全文件強制套用。這是非阻擋美觀優化，API 屬性讀回與人工分頁視覺分開判定。既有單一短目已有人工作出改善回報，不外推為所有長文或所有裝置通過。

### 4. 真正底線與長文安全續寫

依新舊文本差異，映射到最新讀取的各欄實際字元範圍，再用原生 underline style。刪字畫現行欄、增字畫修正欄、替換兩欄分別畫；未變動文字與所有結構性空白（含 U+3000）不畫底線。整條新增的現行欄是「（本條新增）」且不畫底線，修正欄只畫新增文字；整條刪除的修正欄是「（刪除）」且不畫底線，現行欄畫舊文字、排除空白。純重新編號不把全文當實質修正；連動引用修正另列。跨法規移入與新增／刪除標記照既有法律規則。

讀回各欄有效 text runs（包括樣式繼承）與其文字，檢查不是只看 request 裡送了 underline。以「七」→「五」為例，若讀回「日前」也被畫底線，先記錄為缺陷；確認目前人為修改與範圍後，用新 revision 僅校正受影響的 AI 格式，再讀回。不可清掉整份文件或協作者的底線來重做，也不可把校正前結果列為直接 PASS。

每批已驗證才推進 checkpoint：副本／tab ID、觀察 revision、完成的條次／列 ID、實際文字與格式核對、未完成項目。中斷恢復先讀回並核對 checkpoint；前批結果不明時確認是否已寫入，避免重複列／重複文字／再複製母版。協作者修改保留，重疊或政策有變才釐清；不強制覆寫、不重送過期 request，也不自動建立 DOCX。

長條文、多項款目或兩欄長短不等仍保留同一邏輯列，不拆斷法律段落補頁、不截字、不重複、不換錯欄。原生重複表頭／允許長列跨頁等控制須依實際工具確認，不能照抄 Word 的 OOXML 屬性宣稱 Google Docs 有效。缺少分頁控制時揭露限制，另以真實渲染逐頁看長列接續、表頭、裁切與空白頁；不得只因 API 文字完整就稱分頁正確。

### 5. 完成條件與人工驗收

交付前逐列比對來源、最終修正文字及理由，檢查完整範圍的佔位／樣本殘留、漏條、重複、欄位錯配及底線範圍；核對格式契約的指定值與可取得的讀回值。不能讀回的項目列為未驗證，缺資料／失敗單元列為未完成。回報副本身分、已完成項目、最後驗證 revision、操作失敗原因與未知結果，保留現況。

使用者對母版原型的驗收和本次輸出驗收分開。對實際副本收取人工視覺驗收，包含標題與換頁、14／12 pt、三欄等寬、長文接續、字型、底線及項款目；記錄平台／裝置與檢查範圍。不把較早 ChatGPT 工具實測轉成這個 Skill／模型的通過證據。六組必要情境與證據欄位見 [母版驗收案例](acceptance/google-docs-template.md)。

## 後續平台人工驗收（依案例分開記錄）

僅使用明確授權的虛構文件，記錄平台、工具、Skill commit、文件 ID、revision、修改範圍與實際回應，勿記錄憑證。依序驗收無文件建立、既有文件局部編輯、逐項讀回、人工同時修改時拒絕舊版本、無權限／無條件寫入／操作失敗時停止且不建立替代文件、使用者明確選擇 DOCX 時的獨立流程與快照保真。涉及格式再另記視覺與字型驗收；通過其中一項不等於全部通過。不得要求為驗收提供聊天中的密鑰或另造 OAuth 系統。
